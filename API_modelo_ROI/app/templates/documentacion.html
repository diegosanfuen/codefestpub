Overview

API_H7 serves model-based predictions (or dynamic results) based on a context identifier. Each context is associated with a persisted model file.

POST /api_h7/<context> Content-Type: application/json
Key idea: the server first validates that the requested context exists and that its model can be loaded. Then it validates and processes a JSON payload to compute a result.

Endpoint

Use this endpoint to request a prediction/result for the given model context.

Field Description
URL /api_h7/<context>
Method POST
Path Parameter context — string identifier that maps to a stored model route/path.
Request Body JSON payload (see Request).
Response JSON (result or error object).

Request

Send a JSON body containing the features/inputs required by the model for that context. Your service should validate:

  • Content-Type is application/json
  • JSON is parseable (reject invalid JSON)
  • Required fields exist and types are correct
  • No unexpected fields (optional, but recommended for robustness)

Example payload (generic)

{
  "inputs": {
    "feature_1": 123,
    "feature_2": "abc",
    "feature_3": 45.67
  },
}

Adjust the schema to match your model’s required input features. If you maintain a per-context schema, expose it in a “contract/manifest” (see Versioning & Contracts).

Recommended headers

Content-Type: application/json
Accept: application/json
Authorization: Bearer <token>   // if applicable
Tip: If you call this endpoint from a browser, enable CORS safely and restrict origins.

Responses & Status Codes

The endpoint returns JSON. Below are the key response scenarios reflected by your current server logic.

Status When it happens Body shape (example)
200 OK Context exists, model loaded, JSON validated, inference succeeded. 
{
  "context": "my_context",
  "result": {
    "prediction": 0.8123,
    "label": "HIGH"
  },
  "meta": {
    "model_version": "2026-01-30",
    "latency_ms": 23
  }
}
404 Not Found The provided context does not exist in the registry/database. 
{
  "error": "No model associated with this context"
}
500 Internal Server Error Model cannot be loaded (invalid file, incompatible version, corrupted artifact, etc.). 
{
  "ERROR": "Invalid model"
}
400 Bad Request Invalid JSON or schema validation fails (recommended). If not implemented yet, you should add it. 
{
  "error": "Invalid JSON payload",
  "details": "Missing required field: inputs.feature_1"
}
Recommendation: Standardize error keys (e.g., always use error) and include a stable code for client-side logic.

JavaScript (fetch)

async function callApiH7(context, payload) {
  const res = await fetch(`/api_h7/${encodeURIComponent(context)}`, {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "Accept": "application/json",
      "Authorization": "Bearer YOUR_TOKEN"
    },
    body: JSON.stringify(payload)
  });

  if (res.status === 404) {
    const err = await res.json();
    throw new Error(`Unknown context: ${err.error ?? "Not found"}`);
  }
  if (!res.ok) {
    const err = await res.json().catch(() => ({}));
    throw new Error(err.error ?? err.ERROR ?? `Request failed (${res.status})`);
  }

  return res.json();
}

Python (requests)

import requests

url = "http://<host>:<port>/api_h7/<context>"

payload = {
    "is_active_recent": [1],              # 0/1
    "log_legal_events_count": [2.5649],    # log1p(12) aprox
    "log_family_size": [1.3863],          # log1p(3) aprox
    "novelty_x_breadth": [0.3150],         # ejemplo: novelty(0.7) * breadth(0.45)
    "novelty_x_family": [0.9704],          # ejemplo: novelty(0.7) * log_family_size(1.3863)
    "log_priority_count": [1.7918],        # log1p(5) aprox
    "log_party_applicant_count": [1.0986]  # log1p(2) aprox
}

r = requests.post(url, json=payload)
print(r.status_code)
print(r.json())

Error Handling

For a robust product, clients should handle errors by status code and by structured error payload.

Client action Why
Retry only on transient failures (e.g., 502/503/504) Prevents retry storms and avoids repeating invalid requests.
Do not retry 404 It indicates an invalid context; retrying won’t fix it.
Log correlation IDs (if you add them) Enables fast debugging from client logs to server traces.
Surface validation details on 400 Helps users fix payload issues quickly.
Recommended error shape: { "error": "...", "code": "INVALID_PAYLOAD", "details": {...} }

Versioning & Contracts

In production, each context should have a stable, explicit contract describing:

  • Required input fields and types
  • Optional fields and defaults
  • Output schema
  • Model version / training data version / feature order
Best practice: generate a “manifest” (contract) during the model pipeline, store it alongside the model artifact (or in DB), and load it at runtime for validation and documentation.

Example manifest (conceptual)

{
  "context": "my_context",
  "model_artifact": "models/my_context/model.pkl",
  "model_version": "2026-01-30",
  "schema": {
    "inputs": {
      "feature_1": "int",
      "feature_2": "string",
      "feature_3": "float"
    },
    "options": {
      "return_proba": "bool"
    }
  },
  "output": {
    "prediction": "float",
    "label": "string"
  }
}

FAQ

What does “context” represent?

A routing key used to select a specific model (or configuration) from your registry/database.

What should I send in the JSON?

The feature set expected by the model for that context. If you maintain a contract/manifest, you can validate the payload and show precise errors.

Why do I get 500 “Invalid model”?

The server failed to load the model artifact. Common causes include an invalid path, corrupted file, or dependency mismatch (e.g., scikit-learn version incompatibility).

How do I make the API more stable?

Add a manifest-based schema validator, unify error shapes, and include metadata such as model_version and request_id in every response.
